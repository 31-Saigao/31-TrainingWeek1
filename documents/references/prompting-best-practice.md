# 提示技巧最佳實踐(Prompting Best Practices)

## 核心觀念

不要把 CLI agent 當成聊天機器人,它是能**讀取整個專案、自行做決策的 agent**。
把它想像成「今天剛報到的資深工程師」:程式寫得好,但還不熟悉你的專案結構、慣例與歷史包袱。**越好的引導 = 越好的產出。**

### 門的法則(The Door Rule)

**agent 只知道「context window(脈絡視窗)裡有的東西」。** 它看不到你腦中的假設、沒讀過的檔案、口頭講過但沒寫進來的規則。
指令模糊會失敗,通常不是因為它「不夠聰明」,而是**你沒把它需要的資訊放進門內**。

> ❌ 幫我把那個查詢改快一點
>
> ✅ `OrderRepository.GetByCustomer` 在客戶訂單上千筆時很慢(單次約 2 秒)。
> 目前是先 `ToList()` 再用 LINQ 篩選;改成在 EF Core 查詢端就下 `Where` + 分頁。
> ⚠️ 對外回傳格式不變,既有測試要全過。

判斷提示好不好的第一個問題永遠是:**「它需要知道的,我都放進門內了嗎?」**

---

## 一則提示的四段式結構

寫得順的提示,通常同時具備這四段(不必每次全寫,但缺哪段就會在哪裡失準):

1. **角色(Role)** —— 定位它用什麼身分、什麼詞彙層級做事。
   > 你是熟 ASP.NET Core 的資深後端工程師,重視既有慣例勝於個人偏好。
2. **任務(Task)** —— 用**具體動詞**講要做什麼,別用「處理一下」這種模糊詞。
   > 在 `OrdersController` 新增一支 `GET /api/orders/{id}` 查詢端點。
3. **脈絡(Context)** —— 把**真正要處理的材料**放進來(檔案路徑、錯誤訊息、範例),不是只描述它存在。
   > 參考 `Controllers/OrdersController.cs` 既有的建構子注入與 `try/catch` 寫法;DTO 放 `ViewModels/`。
4. **輸出格式(Output Format)** —— 指定要的結構:先給計畫再動手、回傳 JSON、列出改動檔案清單等。
   > 先用三行講你打算怎麼做再開始;完成後列出所有改動的檔案。

> **合起來看**:把上面四段接成一段,就是一則能一次到位的提示。下面的「十個提示模式」是這個骨架在不同情境下的實戰變化。

## 十個提示模式

### 1. 明確指向既有範例

指向具體檔案讓它模仿風格,import、錯誤處理、回傳格式才會一致。

> ❌ 幫我加一支訂單查詢 API
>
> ✅ 參考 `Controllers/OrdersController.cs` 的寫法新增一支訂單查詢 API:
> 用同樣的 `[ApiController]` + 建構子注入 repository、同樣的 `try/catch` 包法、
> 查無資料回 `NotFound()`、成功回 `Ok(dto)`。DTO 放在 `ViewModels/`。

### 2. 描述「結果」而非「步驟」

講清楚使用者要達成什麼,別逐步規定怎麼做,agent 常能找到更好的路。

> ❌ 建一個 component、加 useState 存布林值、綁 onChange 更新、再寫個 useEffect 打 API
>
> ✅ 使用者在設定頁要能開關「出貨 Email 通知」。
> 關閉後,該使用者的訂單出貨時就不寄信;設定要立即生效並持久化,重新整理後維持原狀態。

### 3. 約束三明治(Constraint Sandwich)

一句話包三層:**想要的結果 + 具體限制 + 品質標準**,防止範圍失控。

> ❌ 幫設定頁加深色模式
>
> ✅ 在設定頁加入深色模式(結果);
> 沿用既有的 `ThemeProvider`,不要引入新套件,只改 `app/settings/` 底下的檔案(限制);
> Tailwind class 命名沿用現有慣例,深/淺色都要測過對比度(品質)。

### 4. 先讀再寫

要求它先看過相關目錄,避免重造已有的工具。

> ❌ 幫我寫一個確認對話框 component
>
> ✅ 先讀 `app/components/ui/` 和 `app/lib/utils.ts`,確認有沒有現成的 Dialog 或 cn() helper;
> 有就沿用、沒有再新建。看完先告訴我你打算怎麼做,再動手。

### 5. 資深工程師框架(修 Bug 用)

明確要求修「原始碼」而非改測試,避免它為了讓測試變綠而改壞規格。

> ❌ 測試沒過,幫我修到過
>
> ✅ `OrderRepositoryTests.GetByCustomer_ReturnsOnlyActive` 失敗了。
> 修正底層程式碼,不要改測試。
> 如果你判斷是測試本身寫錯,先解釋原因給我聽,經我同意再改測試。

### 6. 分階段 + 檢查點

大工作拆成可審查的小步驟,每步之間 commit;出錯幾分鐘就能回退,不會累積成災難。

> ❌ 幫我把訂單搜尋功能整套做完
>
> ✅ 分三步,每步做完先停下讓我確認再 commit:
> (1) 在 Core 加 `IOrderSearchService` 介面與 model;
> (2) 在 Infrastructure 實作並補單元測試;
> (3) 接上 `OrdersController` 與 `Search.cshtml` 畫面。

### 7. 提供「為什麼」

給出業務背景,它才能在實作細節上做對決策。

> ❌ 幫 `/api/public/orders` 加流量限制
>
> ✅ 爬蟲用單一 IP 每分鐘打 `/api/public/orders` 一萬次,把 DB 拖垮。
> 幫我加上以 IP 為單位的流量限制;我們沒有 Redis,請用記憶體內方案,
> 正常使用者(每分鐘幾十次)不能被擋到。

### 8. 遷移模式(Migration)

指定**來源 + 目標 + 驗證方式**,讓它自己確認沒搬壞。

> ❌ 把 auth 那些 API 搬到新資料夾
>
> ✅ 把 `pages/api/auth/` 底下所有路由遷移到 `app/api/auth/`(App Router 寫法),
> 對外行為、路徑、回傳格式完全不變;
> 搬完跑 `npm test` 確認既有測試全過,並列出你改動的檔案清單。

### 9. 帶脈絡除錯

別只說「壞了」,給出能縮小範圍的線索:何時開始、錯誤訊息、你已排除的可能。

> ❌ 登入壞掉了,幫我看看
>
> ✅ 在 commit `abc123` 之後,按「登入」出現白畫面。
> 瀏覽器 Console 沒有錯誤,Network 顯示 callback 回 200,但之後 redirect 沒發生。
> 我懷疑是 code 交換或 redirect URL 比對出問題,先從這兩處查起。

### 10. 重構要有安全網

搬移程式碼時保留對外 API,避免呼叫端默默壞掉。

> ❌ 把 `lib/resend.ts` 拆成多個檔案
>
> ✅ 把 `lib/resend.ts` 按功能拆進 `lib/emails/`(如 `order.ts`、`shipping.ts`),
> 但原本 `lib/resend.ts` 要用 re-export 保留所有函式,讓既有 import 完全不用改。
> 完成後跑 `npm run build` 和測試確認沒有壞掉的引用。

## 依任務挑模型

不是每件事都要用最強的模型。**把模型能力對齊任務難度**,又快又省又不失準:

- **快模型(如 Claude Haiku)** —— 適合明確、機械性的工作:抽取欄位、分類、改字串、套版型、跑 grep 找位置。
  > 讀 `appsettings.json`,把所有連線字串的 key 列成一張表。
- **推理模型(如 Claude Opus)** —— 適合需要規劃、跨檔推理、除錯的工作:設計介面、追一個難重現的 bug、拆解大型重構。
  > 訂單出貨後庫存偶爾沒扣,只在高併發時發生;請找出 race condition 的根因並提修法。

> Codex 使用者對應:輕量任務用較快的模型設定,複雜規劃/除錯切到較強的推理模型,判斷原則相同。

⚠️ 反過來也要注意:用快模型硬做複雜規劃,會得到看似合理但漏洞多的產出;用強模型做瑣事則是浪費時間與額度。

## 讓它產出結構化輸出

需要「可被程式或人穩定接手」的結果時,直接指定輸出結構,不要讓它自由發揮:

- **JSON / 表格** —— 要餵給下一個步驟或程式解析時。
  > 把這批訂單的異常原因整理成 JSON 陣列,每筆含 `orderId`、`reason`、`suggestedAction` 三個欄位。
- **先思考再結論(分段)** —— 難題要它先攤開推理再下結論,你才看得到判斷依據、好抓錯。
  > 先在「分析」段落逐點推敲可能原因,再在「結論」段落給出你最有把握的一項與修法。
- **Markdown** —— 要給人讀的說明、清單、步驟時(本文件就是)。

⚠️ 只描述「我要 JSON」常常不夠;把**確切欄位名**也寫出來,回傳格式才會穩定、每次一致。

## 常駐脈絡檔:CLAUDE.md / AGENTS.md

在專案根目錄放一份常駐脈絡檔(Claude Code 讀 `CLAUDE.md`,Codex 讀 `AGENTS.md`),agent 每次都會自動讀取,省去重複交代技術棧與規則。

```markdown
# 專案:OrderHub

## 技術棧

- ASP.NET Core MVC (.NET 8)、EF Core、SQL Server

## 慣例

- Controller 參考 OrdersController.cs 的錯誤處理與回傳格式
- Service 介面放 Core/Services,實作放對應專案

## 禁止事項

- 不要改動 Migrations 已產生的檔案
- 不要在未詢問下新增第三方套件
```

## 一句話總結

**把 CLI agent 當成第一天上班的資深工程師來帶** ——
指向範例、說清結果與原因、給約束、分階段、留安全網,產出品質就會大幅提升。
